# 커피 주문 앱


## 1. 프로젝트 개요



### 1.1 프로젝트명
커피 주문 앱


### 1.2 프로젝트 목적
사용자가 커피 메뉴를 주문하고, 관리자가 주문을 관리할 수 있는 간단한 폴스택 웹 앱
### 1.3 개발 범위
-주문하기 화면(메뉴 선택 및 장바구니 기능)
-관리자 화면(재고 관리 및 주문 상태 관리)
-데이터를 생성/조회/수정/삭제할 수 있는 기능

## 2. 기술 스택 
-프런트엔드: HTML, CSS, 리액트, 자바스크립트
-백엔드: Node. js, Express
-데이터베이스: PostafreSQL

## 3. 기본 사항
-프런트엔드와 백엔드를 따로 개발
-기본적인 웹 기술만 사용
-학습 목적이므로 사용자 인증이나 결제 기능은 제외
-메뉴는 커피 메뉴만 있음

## 4. 주문하기 화면

### 4.1 목적
사용자가 커피 메뉴와 추가 옵션을 선택해 장바구니에 담고, 주문 내역과 총 금액을 확인한 뒤 주문을 접수할 수 있도록 한다.

### 4.2 화면 구성
- 상단 내비게이션에 서비스명 `COZY`와 `주문하기`, `관리자` 메뉴를 표시한다. `주문하기` 화면이 현재 화면임을 구분한다.
- 메뉴 영역에 주문 가능한 커피를 카드 형태로 표시한다. 각 카드에는 메뉴 이미지, 메뉴명, 기본 가격, 간단한 설명, 추가 옵션과 `담기` 버튼을 표시한다.
- 와이어프레임의 예시 메뉴는 아메리카노(ICE), 아메리카노(HOT), 카페라떼이며, 실제 메뉴와 가격은 관리자가 등록한 데이터를 사용한다.
- 장바구니 영역에 선택한 메뉴, 선택 옵션, 수량, 항목별 금액, 총 금액과 `주문하기` 버튼을 표시한다.

### 4.3 기능 요구사항
1. 화면 진입 시 주문 가능한 커피 메뉴와 각 메뉴의 옵션을 조회해 표시한다.
2. 사용자는 메뉴 카드에서 옵션을 선택한 후 `담기`를 눌러 장바구니에 추가할 수 있다. 선택하지 않은 옵션은 주문에 포함하지 않는다.
3. 메뉴 가격에 선택 옵션의 추가 금액을 더해 장바구니 항목 금액을 계산한다. 수량이 여러 개인 경우 항목 금액은 옵션 적용 단가와 수량을 곱해 계산한다.
4. 동일한 메뉴와 옵션 조합을 다시 담으면 해당 항목의 수량을 증가시킨다. 옵션 조합이 다르면 별도 항목으로 구분한다.
5. 장바구니의 총 금액은 모든 항목 금액의 합계로 표시하고, 장바구니 변경 시 즉시 다시 계산한다.
6. 장바구니가 비어 있으면 비어 있음을 안내하고 주문을 접수할 수 없도록 한다.
7. 사용자가 `주문하기`를 누르면 장바구니 내역과 금액으로 주문을 생성한다. 주문 데이터에는 주문 항목, 수량, 선택 옵션, 적용 가격, 총 금액 및 주문 상태가 포함된다.
8. 주문 접수는 결제 없이 진행한다. 접수 성공 시 성공 안내를 표시하고, 접수한 주문이 관리자 화면의 주문 목록에서 확인 가능하도록 한다.
9. 메뉴 조회 또는 주문 접수에 실패하면 사용자에게 오류를 안내한다. 주문 접수 실패 시 장바구니 내역을 유지해 다시 시도할 수 있도록 한다.

### 4.4 화면 동작 및 표시 기준
- 가격은 원화 기준으로 표시하며, 메뉴 기본 가격, 옵션 추가 금액, 항목 금액 및 총 금액을 혼동 없이 구분한다.
- 와이어프레임의 계산 예시는 아메리카노(ICE) 1잔(샷 추가 500원) 4,500원과 아메리카노(HOT) 2잔 8,000원으로 총 12,500원이다.
- 메뉴가 없거나 불러올 수 없는 경우에도 빈 화면으로 남기지 않고 적절한 안내를 표시한다.
- 작은 화면에서도 메뉴와 장바구니 내용을 확인하고 주문할 수 있도록 화면을 반응형으로 구성한다.

### 4.5 완료 기준
- 메뉴 목록에서 메뉴명, 가격, 설명, 옵션 및 담기 기능을 확인할 수 있다.
- 옵션을 선택해 담은 메뉴의 가격과 수량이 올바르게 계산되고 장바구니에 표시된다.
- 서로 다른 메뉴 또는 옵션 조합이 올바르게 구분되며 총 금액이 항목 금액 합계와 일치한다.
- 비어 있는 장바구니는 주문할 수 없고, 유효한 장바구니는 결제 없이 주문으로 접수된다.
- 접수된 주문이 관리자 화면에서 조회되고, 실패 상황에서는 오류 안내와 장바구니 데이터가 유지된다.

## 5. 관리자 화면

### 5.1 목적
관리자가 전체 주문과 주문 상태를 확인하고, 메뉴별 재고 수량을 조정할 수 있도록 한다.

### 5.2 화면 구성
- 상단 내비게이션에 서비스명 `COZY`와 `주문하기`, `관리자` 메뉴를 표시한다. `관리자` 화면이 현재 화면임을 구분한다.
- 관리자 대시보드에 총 주문 수와 상태별 주문 수(주문 접수, 제조 중, 제조 완료)를 표시한다.
- 재고 현황 영역에 메뉴별 메뉴명, 현재 재고 수량, 수량을 1개 늘리는 `+` 버튼과 1개 줄이는 `-` 버튼을 표시한다.
- 주문 현황 영역에 주문 시각, 주문 메뉴 및 수량, 주문 금액, 현재 상태와 상태 변경 기능을 표시한다. 한 주문에 여러 메뉴가 포함될 수 있으므로 주문 항목을 모두 확인할 수 있어야 한다.
- 와이어프레임의 메뉴명과 수량은 표시 예시이며, 실제 데이터베이스에 등록된 메뉴와 재고를 사용한다.

### 5.3 기능 요구사항
1. 화면 진입 시 메뉴별 재고와 주문 목록을 조회하고, 대시보드에 총 주문 수 및 상태별 주문 수를 표시한다.
2. 재고 `+` 버튼을 누르면 해당 메뉴의 재고를 1개 증가시키고, `-` 버튼을 누르면 1개 감소시킨다. 변경 결과는 저장되어 화면을 다시 불러와도 유지된다.
3. 재고는 0개 미만이 될 수 없다. 재고가 0개일 때 `-` 조작은 재고를 변경하지 않으며, 재고 부족 상태를 사용자에게 명확히 표시한다.
4. 주문 현황에는 각 주문의 접수 시각, 메뉴별 주문 수량 및 옵션, 총 금액과 주문 상태를 표시한다.
5. 관리자는 주문 상태를 `주문 접수`에서 `제조 중`, `제조 중`에서 `제조 완료`로 변경할 수 있다. 각 주문에는 현재 상태에 맞는 다음 단계 동작만 제공한다.
6. 주문 상태를 변경하면 해당 주문과 대시보드의 상태별 집계가 즉시 갱신된다.
7. 주문 목록과 집계는 사용자 화면에서 접수한 주문을 반영하며, 주문이 없을 때는 빈 상태 안내를 표시한다.
8. 재고 또는 주문 정보를 불러오거나 변경하는 데 실패하면 오류를 안내한다. 저장되지 않은 변경을 성공한 것처럼 표시하지 않는다.

### 5.4 화면 동작 및 표시 기준
- 주문 상태 명칭은 `주문 접수`, `제조 중`, `제조 완료`로 통일한다.
- 대시보드의 총 주문 수는 조회 대상 주문 전체 수이며, 상태별 수의 합계와 일치한다.
- 재고 수량은 메뉴별로 표시하고, 증감 후 최신 값을 화면에 반영한다.
- 주문 시각과 금액, 메뉴명 및 수량을 한 주문 단위로 명확히 구분해 표시한다.
- 작은 화면에서도 대시보드, 재고 조작 및 주문 상태 확인이 가능하도록 반응형으로 구성한다.

### 5.5 완료 기준
- 관리자가 대시보드에서 전체 주문 수와 주문 상태별 건수를 확인할 수 있다.
- 메뉴별 재고가 표시되며 `+`/`-` 버튼으로 1개씩 조정되고, 0개 미만으로 내려가지 않는다.
- 주문 목록에서 주문 시각, 모든 주문 항목, 수량, 옵션, 금액 및 현재 상태를 확인할 수 있다.
- 주문 상태를 다음 단계로 변경하면 저장된 상태와 대시보드 집계가 함께 갱신된다.
- 조회 또는 변경 실패 시 오류가 안내되고, 저장되지 않은 정보가 성공한 것처럼 표시되지 않는다.

## 6. 백엔드 개발 PRD

### 6.1 목적 및 범위
- 프런트엔드와 별도로 Node.js와 Express를 사용한 REST API 서버를 개발한다.
- PostgreSQL에 메뉴, 옵션, 주문 및 주문 항목을 저장한다.
- 메뉴 조회, 주문 접수, 재고 차감, 주문 조회 및 주문 상태 변경을 제공한다.
- 사용자 인증과 결제는 범위에 포함하지 않는다.

### 6.2 데이터 모델

#### Menus
커피 메뉴 및 현재 재고를 저장한다.
- `id`: 기본 키
- `name`: 커피 이름
- `description`: 메뉴 설명
- `price`: 메뉴 기본 가격(원, 0 이상의 정수)
- `image_url`: 메뉴 이미지 경로 또는 URL
- `stock_quantity`: 현재 재고 수량(0 이상의 정수)
- `is_available`: 주문 가능 여부
- `created_at`, `updated_at`: 생성·수정 시각

#### Options
메뉴에 연결할 수 있는 추가 옵션을 저장한다.
- `id`: 기본 키
- `menu_id`: 연결 메뉴 ID, `Menus.id` 참조
- `name`: 옵션 이름
- `price`: 옵션 추가 가격(원, 0 이상의 정수)
- `is_available`: 선택 가능 여부
- `created_at`, `updated_at`: 생성·수정 시각

#### Orders
주문 단위의 정보를 저장한다.
- `id`: 기본 키
- `ordered_at`: 주문 접수 시각
- `status`: 주문 상태. `received`(주문 접수), `preparing`(제조 중), `completed`(제조 완료) 중 하나
- `total_amount`: 주문 총 금액(원, 0 이상의 정수)

#### OrderItems 및 OrderItemOptions
주문 당시의 메뉴·옵션·가격을 보존하기 위해 주문 상세를 별도 테이블에 저장한다. 메뉴나 옵션의 이름·가격이 나중에 바뀌더라도 과거 주문 내역은 접수 시점의 값으로 표시한다.
- `OrderItems`: `id`, `order_id`, `menu_id`, `menu_name`, `quantity`, `unit_price`, `line_amount`
- `OrderItemOptions`: `id`, `order_item_id`, `option_id`, `option_name`, `unit_price`
- `OrderItems.order_id`는 `Orders.id`를 참조한다. `menu_id`는 원본 메뉴와 연결하되, 주문 시점의 메뉴명·단가도 보관한다.
- `OrderItemOptions.order_item_id`는 `OrderItems.id`를 참조한다. 옵션이 없는 주문 항목은 관련 행이 없다.
- 모든 가격은 원화 정수로 저장한다. `unit_price`는 메뉴 기본 가격과 해당 주문 항목에 선택된 옵션 가격을 합산한 1개당 가격이며, `line_amount`는 `unit_price × quantity`이다. `Orders.total_amount`는 모든 주문 항목 금액의 합계다.

### 6.3 사용자 흐름 및 처리 규칙
1. 주문 화면에 진입하면 프런트엔드는 메뉴와 각 메뉴의 옵션을 API로 조회한다. 관리자 화면은 동일한 메뉴 정보에서 재고 수량도 표시하며, 고객 주문 화면에는 재고 관리용 수량을 노출하지 않는다.
2. 사용자가 메뉴와 옵션을 골라 장바구니에 담는다. 장바구니는 주문을 제출하기 전까지 프런트엔드에서 관리한다.
3. 사용자가 `주문하기`를 누르면 메뉴 ID, 수량, 선택 옵션 ID를 서버로 전송한다. 브라우저가 계산한 금액은 신뢰하지 않으며, 서버가 데이터베이스의 최신 메뉴·옵션 가격으로 주문 금액을 계산한다.
4. 서버는 주문 항목 검증, 재고 확인 및 차감, 주문과 상세 항목 저장을 하나의 데이터베이스 트랜잭션으로 처리한다. 일부 항목이라도 재고 부족, 메뉴/옵션 사용 불가 또는 유효성 오류가 있으면 전체 처리를 취소해 재고와 주문 데이터가 부분적으로 저장되지 않게 한다.
5. 주문이 성공하면 기본 상태 `received`(화면 표시: `주문 접수`)로 저장하고 생성된 주문 정보를 응답한다. 프런트엔드는 성공 응답을 받은 경우에만 장바구니를 비우고 성공 안내를 표시한다. 실패 시 장바구니를 유지한다.
6. 관리자 화면은 주문 목록과 재고를 조회한다. 주문 상세에는 접수 시각, 메뉴, 수량, 선택 옵션, 금액 및 상태를 표시한다.
7. 관리자가 주문 상태를 변경하면 서버는 허용된 다음 단계만 저장한다: `received` → `preparing` → `completed`. 그 외 상태 전이는 거부한다.
8. 관리자의 재고 증감은 서버에 저장하며, 재고가 0 미만이 되는 변경은 거부한다.

### 6.4 API 설계
모든 경로는 `/api`를 기본 접두사로 사용한다. 성공 응답은 JSON을 반환하며, 오류 응답에는 프런트엔드가 안내에 사용할 수 있는 `error` 메시지를 포함한다.

| 메서드 및 경로 | 용도 | 주요 응답 |
|---|---|---|
| `GET /api/menus` | 주문 가능한 메뉴와 메뉴별 선택 가능한 옵션 조회. 관리자 화면에서도 재고 표시를 위해 사용 | 메뉴 ID, 이름, 설명, 가격, 이미지, 재고 수량, 옵션 목록 |
| `POST /api/orders` | 주문 생성, 재고 검증·차감, 주문 및 상세 저장 | `201 Created`, 생성된 주문 전체 |
| `GET /api/orders` | 관리자 주문 현황 목록 조회 | 주문 목록과 각 주문의 항목·옵션·금액·상태 |
| `GET /api/orders/:orderId` | ID로 주문 한 건 조회 | 주문 전체와 주문 항목 |
| `PATCH /api/orders/:orderId/status` | 주문 상태를 다음 단계로 변경 | 갱신된 주문과 상태 |
| `PATCH /api/menus/:menuId/stock` | 관리자가 재고를 지정한 수량만큼 증감 | 갱신된 메뉴와 최신 재고 수량 |

#### `POST /api/orders` 요청 예시
```json
{
  "items": [
    {
      "menuId": 1,
      "quantity": 2,
      "optionIds": [3]
    },
    {
      "menuId": 2,
      "quantity": 1,
      "optionIds": []
    }
  ]
}
```
- `items`는 비어 있지 않아야 한다. `quantity`는 1 이상의 정수여야 하며, 같은 메뉴와 옵션 조합은 하나의 항목으로 합쳐서 제출한다.
- 서버는 메뉴와 옵션의 존재 여부, 주문 가능 여부 및 옵션의 해당 메뉴 연결 여부를 확인한다.
- 메뉴별 주문 수량을 합산해 재고와 비교한 뒤 차감한다. 재고가 부족하면 `409 Conflict`를 반환하고 주문은 생성하지 않는다.
- 유효하지 않은 요청은 `400 Bad Request`, 존재하지 않는 리소스는 `404 Not Found`를 반환한다.
- 성공 응답에는 `id`, `orderedAt`, `status`, `items`, `totalAmount`를 포함한다. 각 항목에는 메뉴명, 수량, 선택 옵션, 단가 및 항목 금액을 포함한다.

#### 상태 변경 및 재고 조정 요청
- `PATCH /api/orders/:orderId/status` 본문: `{"status":"preparing"}` 또는 `{"status":"completed"}`. 현재 상태에서 바로 다음 단계가 아닌 변경은 거부한다.
- `PATCH /api/menus/:menuId/stock` 본문: `{"adjustment":1}` 또는 `{"adjustment":-1}`. `adjustment`는 0이 아닌 정수여야 하며, 결과 재고가 음수가 되면 `409 Conflict`를 반환한다.

### 6.5 오류 처리 및 일관성
- 메뉴·주문 조회 및 변경 실패는 적절한 HTTP 오류 상태 코드와 JSON 오류 메시지로 반환한다. 서버 오류는 `500 Internal Server Error`로 응답한다.
- 주문 저장과 재고 차감, 주문 상태 변경은 데이터베이스 트랜잭션으로 처리해 부분 저장을 방지한다.
- 동시 주문으로 재고가 중복 차감되지 않도록 재고 검증과 차감은 원자적으로 수행한다.
- 프런트엔드는 오류 응답을 성공으로 처리하지 않고 사용자에게 오류를 표시한다. 주문 접수 실패 시 장바구니를 보존한다.

### 6.6 백엔드 완료 기준
- 메뉴와 연결된 옵션을 데이터베이스에서 조회해 주문 화면에 필요한 정보를 제공한다.
- 유효한 주문은 주문 시점의 가격·옵션·금액과 기본 상태를 포함해 저장되고, 메뉴 재고가 같은 트랜잭션에서 차감된다.
- 재고 부족 또는 잘못된 메뉴·옵션 요청은 주문과 재고를 변경하지 않고 명확한 오류로 응답한다.
- 관리자 주문 목록 및 주문 ID별 조회에서 저장된 주문 전체 내용을 확인할 수 있다.
- 관리자 재고 조정 및 주문 상태 변경이 저장되고, 잘못된 변경은 거부된다.
- API 오류, 데이터베이스 오류 또는 재고 부족이 프런트엔드에서 사용자에게 안내되며 실패한 주문의 장바구니가 유지된다.
